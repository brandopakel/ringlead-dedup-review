Internal tooling · Salesforce data quality

How the merge QA tool decides what you have to look at

Every week a RingLead deduplication resolution produces a few hundred groups of suspected duplicate Leads, and someone has to confirm each merge is right before it runs. This tool reads the resolution export and answers one question per group: does a human need to open this?

222 460 groups needing review, from a real run.
238 were cleared automatically.

The finding the whole tool is built on

In that run, 293 of 460 groups had completely different corporate email domains — the two records looked like they worked at different companies. That sounds like the matching is broken. It isn't.

ZoomInfo enrichment overwrites Company and Title on every record with the person's current employer, while Email, Domain and the Account link stay frozen at whatever job they were captured under. So name-and-company matching works, and a mismatched email domain is normal rather than suspicious.

That single fact rules out the obvious check. Flagging every domain mismatch would flag 64% of the file and save nobody any time.

Question one: is this actually one person?

Since name and company can't settle it, identity rests on evidence that survives a job change. Three fields carry it, and they agree far more often than they conflict.

Groups where two or more records both carry the field, from the same run.
SignalAgree DisagreeVerdict
LinkedIn profile3744 Strongest single signal
ZoomInfo Contact ID3896 Survives job changes by design
Mobile number32313 Personal line, follows the person
Phone143213 Not used — company switchboard, changes with the job

When any of those agree across records, the group is confirmed as one person. When one actively disagrees, the group is flagged as possibly two different people who share a name. When none are present at all, the group is flagged as unverifiable — the tool will not guess.

Why Phone is excluded. It disagreed in 213 of 356 groups, because it is usually the company's main line. Including it would have produced hundreds of false alarms while adding nothing the other three don't already say.

Question two: is the merge output right?

Separately from identity, the tool checks the merge preview itself. The most common defect: the surviving record keeps an email that doesn't belong to the employer it claims to work for.

Group 4820001234 · illustrative example Needs a fix
Company Northwind Logistics
After merge d.whitfield@oldcarrier.comkept, but stale
Discarded dwhitfield@northwind-logistics.commatches employer
Should be dwhitfield@northwind-logistics.comtool's recommendation

This fired on 102 groups. The tool also checks whether the merge keeps an outdated job title, points at a former employer's Account, demotes the lead's funnel stage, overwrites first-touch attribution, or hands the record to a deactivated user.

"After merge" is a prediction, not a target. RingLead's own column shows what will happen, defects included. Where the correct value can be derived from the data, the report states it separately as Should be. Where it can't — a possible false match, a master choice needing judgement — no target is offered, because a confident guess would be worse than silence.

How something earns a place in the queue

Findings come in three severities, and only the first two send a group to review.

Critical
Demonstrably wrong output. The data names both the defect and the correct value.
Review
Can't be settled from the data. A person has to decide.
Contributor
Suspicious but common. Shown as context; only matters stacked with others.

The discipline that keeps the queue small is a single rule: a contributor firing on more than a quarter of the file is describing the routine shape of a merge, not evidence of a problem — so it carries zero weight. It still displays, but it can never push a group into the queue on its own.

In the sample run that zeroed four signals that each looked meaningful in isolation: ownership consolidating (250 of 460 groups), duplicates on different Accounts (160), first-touch attribution overwritten (169), and high-value fields dropped (135). Without that rule the queue swallowed 57% of the file instead of 48%.

What a run produces

Four files, aimed at three different people.

FileForWhat it's for
_qa.htmlthe reviewer The review queue, with per-group evidence and recommended values. Progress is saved locally, so the queue can be worked across sessions.
_survivorship_changes.mdwhoever owns the RingLead criteria Settings to change once, ranked by how many groups each clears. Usually the highest-leverage output — most defects collapse into a handful of rule changes.
_master_changes.csvwhoever owns the RingLead criteria Groups where a different record should be the master. Applied in RingLead before merging.
_corrections.csvwhoever has Salesforce write access Field values to correct after the merge runs, Data Loader-shaped, each new value beside the one it replaces.

These two are sequenced, not parallel

A correction edits a field on the record that survives. A master change alters which record survives — so the surviving record's ID changes, and any field correction computed against the old preview becomes wrong. Groups needing a new master are deliberately withheld from the correction sheet; applying them would write values onto a record that is about to be deleted.

  1. Apply the master changes in RingLead.
  2. Re-export the resolution and re-run the tool.
  3. Apply the correction sheet after the merge.

Checking it yourself

Nothing here is a black box, and none of it needs Salesforce or RingLead credentials — the tool only ever reads an exported CSV. 

python main.py --open      # newest export in data/, opens the report
python -m pytest           # the comparison logic that decides auto-approval

Where the decisions live:

  • ringlead_qa/rules.py — every check, its severity, and the review threshold. Each rule is a small function with the reasoning in a comment above it.
  • ringlead_qa/fields.py — which fields count as high-value, which are routing, which are system noise that can never count as data loss, and the funnel ordering used to detect a demotion.
  • ringlead_qa/normalize.py — how two values are judged equal. This is where a company like Meridian Holdings is matched to meridian.com, and it's covered by tests, because a change here silently changes which groups get auto-approved.
The most useful thing to audit is the list of auto-approved groups, not the flagged ones. A false alarm costs a minute; a group wrongly cleared merges two people into one record. A hand-audit of a random sample found every cleared group had matching LinkedIn, ZoomInfo ID and mobile across its records.

Known limits

  • Leads only so far. Account and Contact resolutions use the same export structure but different column names, so the field catalog needs an entry per entity type before any of the rules mean anything there.
  • Domain aliases that share no letters with the company name can't be inferred — a company trading under an unrelated legacy domain surfaces as a review item rather than being silently matched.
  • Title freshness relies on enrichment dates as a recency proxy. A record that was never enriched can't win a freshness comparison.
  • Recency is applied per field class, not globally. Current-state fields take the freshest value; history fields such as Lead Source take the oldest. Treating recency as universally correct would flag 316 of 460 groups.
Examples on this page are synthetic. No customer records leave the machine the tool runs on — exports, reports and correction sheets are all git-ignored.
